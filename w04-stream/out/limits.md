## A4 · 두 성장률

주장하지 않고 내 숫자로 검산한다. n 을 4배 할 때마다 어떻게 되는지:

| 구간 | exact peak 배율 | fm peak 배율 |
|---|---:|---:|
| 100k → 400k | 11.59 / 3.93 = **2.95×** | 0.97× |
| 400k → 1.6M | 46.65 / 11.59 = **4.02×** | 0.99× |
| 1.6M → 6.4M | 188.3 / 46.65 = **4.04×** | 1.03× |
| 6.4M → 25.6M | 756.4 / 188.3 = **4.02×** | 1.00× |

**exact 는 n^0.96, FM 은 n^0.001 이다** (5점 log–log 최소제곱). 반올림하면 선형 대
상수이고, 그것이 A4 가 보라고 한 것이다.

- **exact 메모리 = distinct 당 약 80 바이트.** 78.9 / 79.4 / 80.1 / 80.5 B (그리고 A2 의
  두 줄에서 81 B 안팎). 400k ~ 102.4M, 256배 범위에서 79 ~ 81 B 로 **3% 안**이다. 첫
  구간만 2.95배로 낮은데, n=100,000 에서는 distinct 당 107.0 B 로 나온다 — `set` 의 해시
  테이블이 2의 거듭제곱 단위로 잡히므로 작은 n 에서는 테이블 여유분이 상대적으로 크다.
  400k 부터 80 B 근처로 수렴하고, 그 뒤로는 조금씩만 올라간다.
- **FM 메모리 = 15,111 ~ 15,646 B.** 256배 범위 전체에서 **약 3.5% 안**이고, 방향성도 없다
  (0.97 → 0.99 → 1.03 → 1.00). 이 값은 데이터가 아니라 **해시 개수**가 정한다:
  64개 추정기의 `tails`·`low_mask`·`a`·`b` 리스트뿐이고, n 이 어디에도 들어가지 않는다.
  스트림을 1,000배 늘려도 같은 15 KB 다.

시간은 둘 다 선형이다 — exact n^1.04, FM n^1.00. 배율로도 exact 4.29 / 4.40 / 4.20 /
4.08, FM 4.05 / 4.04 / 4.01 / 3.94 로 둘 다 4에 붙어 있다. **차이는 지수가 아니라
상수다**: FM 은 아이템당 62 ~ 64 µs, exact 는 0.71 ~ 0.90 µs 로 **70 ~ 88배 느리다.**
평평한 메모리는 공짜가 아니라 시간으로 산 것이고, 그 값은 추정기 하나당 곱셈 한 번씩
× 64다. HyperLogLog 가 존재하는 이유가 바로 이 상수다.

## A5 · FM 은 얼마나 맞았나

| n | fm / true | |
|---:|---:|---|
| 100,000 | **0.84×** | 16% 과소 |
| 400,000 | **0.85×** | 15% 과소 |
| 1,600,000 | **0.98×** | |
| 6,400,000 | **0.98×** | |
| 25,600,000 | **0.96×** | |

**다섯 번 모두 2배 안에 있고, 최악이 0.84× 다.** 요구된 것은 2배이지 몇 퍼센트가
아니므로 이건 방법이 정상 동작한 것이다.

**n 에 따라 좋아지는지 나빠지는지는 이 데이터로 판단할 수 없다.** 0.84 → 0.98 로 올라간
것처럼 보이지만 각 크기에서 hash seed 하나로 한 번씩 잰 값이다. Task 1 에서 같은 규칙을
40회 돌렸을 때 비는 0.68 ~ 1.70 까지 벌어졌고(`out/fm_rules.json`), 그 폭이 0.84 와 0.98 의
차이보다 훨씬 크다. 추세를 말하려면 크기마다 여러 seed 로 재야 한다.

## A2 · exact 가 불쾌해진 지점 — n = 102,400,000 (90.80초), 그리고 바닥난 것은 시간이다

25.6M 까지는 아무것도 불쾌하지 않았다. exact 가 22.93초에 756 MB 이고, 24 GB 기계에서
그건 압박이 아니다. 그래서 더 밀었다.

FM 을 함께 돌린 채로는 밀 수 없었다. FM 은 아이템당 63 µs 로 **n 에 선형**이므로
102.4M 이면 약 1.8시간이다 — 그건 exact 의 한계가 아니라 내 FM 구현의 한계이고, A2 가
묻는 것은 exact 쪽이다. 그래서 아래 두 줄은 **제공된 `task2_limits.exact_distinct()` 를
그대로 호출해 exact 만** 측정했다(`task2_exact_only.py`, 원자료 `out/limits_exact_only.json`).
`task2_limits.py` 는 수정하지 않았고, 그래서 이 두 줄은 `limits.json` 에 없다.

| n | distinct | exact 초 | exact peak | distinct 당 |
|---:|---:|---:|---:|---:|
| 51,200,000 | 18,799,271 | 44.02 | 1,523 MB | 81.0 B |
| **102,400,000** | **37,596,727** | **90.80** | **3,056 MB** | **81.3 B** |

**n = 102,400,000 에서 90.80초.** task2.md 의 A2 는 "genuinely unpleasant" 라고만 하므로
기준은 내가 정했다: 한 번 재는 데 1분 반이 넘게 걸리면, 크기를 바꿔 가며 여러 번 돌리는
작업에는 이미 쓸 수 없다. 같은 지점의 peak 메모리는 3.06 GB 로 24 GB 의 13% 다.

**먼저 바닥난 것은 시간이다.** 그리고 이 격차는 벌어지기만 한다. 가장 큰 측정에서
exact 는 **스트림 아이템당 29.8 B** 를 잡으므로(distinct 가 0.37n 이고 distinct 당 81 B),
메모리가 문제가 되는 지점을 대략 외삽하면 이렇다 (GB = 10⁹ B, 시간은 선형으로 늘린다고 가정):

| 메모리 | 도달하는 n | 그때까지 걸린 시간 |
|---:|---:|---:|
| 8 GB | 약 268M | 약 4분 |
| 16 GB | 약 536M | 약 8분 |
| 24 GB (전부) | 약 804M | **약 12분** |

즉 이 기계에서 RAM 을 다 쓰려면 대략 12분을 기다려야 하고, 그 훨씬 전에 이미 못 쓸 물건이
된다. `set` 이 커질 때 옛 테이블과 새 테이블이 잠깐 공존하는 순간은 이 외삽에 들어 있지
않으므로, 실제 한계는 조금 더 앞에 있다. **exact 를 죽이는 것은 메모리가 아니라 그 앞에 오는
시간이다** — 적어도 24 GB 와 순수 파이썬 `set` 이라는 이 조합에서는.

그리고 그게 왜 FM 이 이기는지를 바꾸지는 않는다. n ≈ 804M 에서 exact 는 24 GB 를 쓰고
FM 은 여전히 15.6 KB 를 쓴다. **약 150만 배다.** 시간이 먼저 무너진다는 사실은 sketch 가
필요 없다는 뜻이 아니라, 한 대에서는 두 벽이 거의 같이 온다는 뜻이다.
