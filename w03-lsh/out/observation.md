# Week 3 · observation

## Task 1 · Minhash과 LSH

**행 단위 1패스:** 행을 하나 읽어 그 행에 1이 있는 열의 서명만 갱신하고 버릴 수 있어서, 메모리에 안
들어가는 행렬에서도 돈다. 열 단위면 열마다 행렬 전체를 다시 읽어야 한다. 행 번호 해시도 행마다 한
번만 계산한다 (`task1_minhash.py` `minhash_signatures`).

**R5 — 남는 행은 앞쪽 `n % b`개 밴드에 한 행씩 더 준다.** 버리면 계산한 서명을 낭비하고, 한 밴드에
몰면 그 밴드만 키가 커져 충돌이 거의 없어진다. 고르게 나누면 밴드 간 차이가 최대 1행이라 §3.4.2 의
S곡선이 그대로 맞는다.

**1.0 대 2/3 은 해시를 늘려야 좁혀진다.** 서명 2개로는 추정값이 0, 0.5, 1 뿐이다. 표준오차
√(s(1−s)/k) 가 k=2 에서 ±0.33 이고, 1/10 로 줄이려면 해시가 100배 필요하다. 비용은 저장·시간 모두
선형이다.

## Task 2 · 크로스오버

**크로스오버 n ≈ 350** (M4 Pro / 24 GB / macOS 27.0.1 / Python 3.14). n=350 에서는 brute 0.1705 초,
LSH 0.1764 초로 brute 가 근소하게 앞서고, 400 에서 0.2242 대 0.1813 초로 뒤집힌다. 350 까지 LSH 가
지는 건 비교를 많이 해서가 아니라, 행 5,003개를 전부 훑는 고정비용 0.105 초 때문이다
(`curve.md` A7·A8).

**A4 2차 검증은 성립했다.** n 을 2배 할 때마다 brute 시간이 4.01 / 3.99 / 4.03 / 4.03 배였고,
비교 횟수는 n(n−1)/2 와 정확히 같았다 (`curve.md` A4).

**n = 6,500 에서 62.26 초로 1분을 넘었고, 먼저 바닥난 건 시간이다.** 그때 brute 메모리는 59.2 KB 였다.
제공 경로는 `bench.build()` 가 2,120개 고정이라 그 위를 잴 수 없어, `task2_extend.py` 로 seed 를

## Task 3 · 비교를 99.99% 줄이기

**n = 128 해시, b = 32 밴드(r = 4), 계단 (1/32)^(1/4) = 0.420 — 임계값 0.6 보다 일부러 아래.** 가장
약한 정답 쌍이 46/74 = 0.622 라 계단이 0.6 이면 절반쯤 놓치지만, 0.42 면 1 − (1 − 0.622⁴)³² = 0.994 로
잡는다. 대가인 오탐은 무관한 쌍(s ≈ 0.006)에서 4×10⁻⁸ 로 사실상 없다. 결과: 비교 124회, recall 100%,
strong (`out/bench.txt`).

**계단을 반대로 옮기면 recall 이 무너진다.** 128 해시를 고정하고 밴드만 바꿔 돌린 결과, b=8 이면 recall
17.4%(비교 21회), b=16 이면 73.6%(89회), b=32 는 100%(124회)였다. 비교가 줄어도 답을 조용히 잃는다.

**해싱을 공짜로 치는 건 이미 부당하다.** 0.32 초 중 비교는 124 × 2.83 µs, 전체의 0.1% 뿐이다. 비교가
지배적이 되려면 후보 쌍 수가 문서 수 × 해시 수(2,120 × 128 = 271,360)를 넘어야 한다.
